① Architecture
JDBC = Java Database Connectivity — a set of interfaces in java.sql. Vendors supply the implementation JAR. It's NOT a class!
Java Application
↓
JDBC API (java.sql interfaces — NOT implementation)
↓
DriverManager — Router / Registry Layer
↓
Vendor Driver JAR e.g. com.mysql.cj.jdbc.Driver
↓
Target RDBMS MySQL / Oracle / PostgreSQL
JDBC is NOT a class — it is a set of interfaces. Vendor JAR contains the actual implementation.
② Core Interfaces
InterfacePackageRole
DriverManagerjava.sqlUtility class. Manages drivers. Factory for Connection objects.
Connectionjava.sqlOpen socket session to DB. Creates Statement objects. Manages transactions.
Statementjava.sqlSends static hardcoded SQL. ⚠️ Vulnerable to injection if user input concatenated.
PreparedStatementjava.sqlPre-compiles parameterized SQL with ? placeholders. ✅ Immune to injection. Cached.
CallableStatementjava.sqlExecutes stored procedures. Extends PreparedStatement.
ResultSetjava.sqlForward-moving cursor over tabular results. Starts before row 1.
DatabaseMetaDatajava.sqlInfo about the DB: tables, columns, driver version, supported features.
ResultSetMetaDatajava.sqlInfo about a ResultSet: column count, names, data types.
③ 7-Step JDBC Lifecycle
1
Import Package
import java.sql.*;
2
Load Driver — Old vs JDBC 4.0
Old (JDBC < 4.0):
Class.forName("com.mysql.cj.jdbc.Driver");
↳ fires static{} block → registerDriver()
JDBC 4.0+ AUTO 🎉
Just add driver JAR to classpath!
SPI reads META-INF/services/java.sql.Driver automatically. No Class.forName() needed!
3
Establish Connection
Java
// URL format: jdbc:subprotocol://host:port/database
Connection con = DriverManager.getConnection("jdbc:mysql://localhost:3306/mydb","root","pass");

// DataSource — POOLED — use in production ✅
DataSource ds = new HikariDataSource(config);
Connection con = ds.getConnection();
URL format: jdbc : subprotocol :// host : port / database
4
Create Statement Object
Java
Statement st = con.createStatement(); // static SQL
PreparedStatement pst = con.prepareStatement("SELECT * FROM t WHERE id=?");
CallableStatement cst = con.prepareCall("{call myProcedure(?,?)}");
5
Execute SQL
Java
ResultSet rs = st.executeQuery("SELECT * FROM students"); // DQL → ResultSet
int n = st.executeUpdate("INSERT INTO students VALUES(1,'A',90)"); // DML → int
boolean b = st.execute("..."); // Either → true=ResultSet, false=int

pst.setInt(1, 101); pst.setString(2, "Navin");
ResultSet rs = pst.executeQuery(); // no SQL string here!
6
Process ResultSet
Java
while(rs.next()) { // cursor moves forward; returns false at end
  int id = rs.getInt("student_id"); // by column name
  String name = rs.getString(2); // by 1-based index!
  double gpa = rs.getDouble("gpa");
}
Columns are 1-indexed. rs.getInt(0) throws SQLException!
7
Close Resources
// Old — explicit finally block
try {
  con=DriverManager.getConnection(...);
} finally {
  if(rs!=null) rs.close();
  if(st!=null) st.close();
  if(con!=null) con.close(); // reverse!
}
// Modern — try-with-resources Java 7+ ✅
try (Connection con=...;
     Statement st=...;
     ResultSet rs=...) {
  while(rs.next()){
    // process
  }
} // auto .close() here!
④ SQL Injection & PreparedStatement
⚠️ EXPLOIT: Input admin'-- makes query:
SELECT * FROM users WHERE username='admin'--' AND password='xyz'
The -- comments out the password check. Attacker logs in as admin with NO password!
Security
// ❌ VULNERABLE — never concatenate user input!
String q = "SELECT * FROM users WHERE user='" + input + "'";

// ✅ SAFE — PreparedStatement
String q = "SELECT * FROM users WHERE user=? AND pass=?";
PreparedStatement pst = con.prepareStatement(q); // compiled once
pst.setString(1, userInput); pst.setString(2, passInput);
ResultSet rs = pst.executeQuery(); // values sent separately — never parsed as SQL
AttributeStatement ❌PreparedStatement ✅
CompilationParse+Compile every callCompiled ONCE, plan reused
SQL InjectionVULNERABLEIMMUNE
PerformanceSlow for repeated queriesFast — cached execution plan
Input bindingAppended into raw SQLBound via setX(index, val)
Use caseOne-time static queries onlyAlways prefer — especially user input
execute()st.executeQuery(sqlString)pst.setX(); pst.executeQuery() — no arg!
⑤ Transactions — commit, rollback, savepoints
A transaction = unit of work: fully committed or fully rolled back. JDBC is auto-commit by default!
Transactions
con.setAutoCommit(false); // Step 1: disable auto-commit
try {
  st.executeUpdate("UPDATE accounts SET balance=balance-500 WHERE id=1");
  st.executeUpdate("UPDATE accounts SET balance=balance+500 WHERE id=2");
  con.commit(); // Step 3: commit if all OK
} catch (SQLException e) {
  con.rollback(); // Step 4: rollback on failure
} finally {
  con.setAutoCommit(true); // restore default
}

⑥ Batch Processing
Instead of N separate INSERTs (N round trips), send all in one network call!
Batch
con.setAutoCommit(false);
PreparedStatement pst = con.prepareStatement("INSERT INTO t VALUES(?,?,?)");

for (Student s : list) {
  pst.setInt(1, s.getId());
  pst.setString(2, s.getName());
  pst.addBatch(); // queue it
}
int[] results = pst.executeBatch(); // one trip!
con.commit();
💡 Commit every 500-1000 rows, not all at once — large transactions hold locks longer!

⑧ Connection Pooling — Production Essential
⚠️ Problem: Creating a new DB connection = ~100-200ms (TCP handshake + auth + session). For 1000 req/sec → catastrophic!
✅ Solution: Connection Pool — cache of pre-opened connections reused across requests.
HikariCP
HikariConfig cfg = new HikariConfig();
cfg.setJdbcUrl("jdbc:mysql://localhost/mydb");
cfg.setMaximumPoolSize(10); // max 10 connections
cfg.setMinimumIdle(2); // keep 2 ready always
cfg.setConnectionTimeout(30000); // 30s timeout

DataSource ds = new HikariDataSource(cfg);
try (Connection con = ds.getConnection()) {
  // returned to pool on .close()!
}

⑪ Real Interview Questions
Google · Amazon · Apple · Microsoft · Meta · Netflix · TCS · Infosys
Q: What is the difference between Statement, PreparedStatement, and CallableStatement?
GoogleAmazonAppleMicrosoft
Statement: static SQL, compiled every time, injection-vulnerable. PreparedStatement: parameterized, compiled once, injection-immune, fast for repeats. CallableStatement: stored procedures, supports IN/OUT/INOUT params.
Q: Why is PreparedStatement preferred over Statement?
AmazonMetaGoogle
3 reasons: 1) Security — prevents SQL injection. 2) Performance — pre-compiled, execution plan cached and reused. 3) Readability — cleaner code with setX() methods instead of string concatenation.
Q: What is connection pooling? Why is it needed?
GoogleAmazonAppleMicrosoft
Pool = cache of pre-created connections reused across requests. Needed because creating a new connection = ~100-200ms. For high-traffic apps, creating per-request connections is a bottleneck. Spring Boot uses HikariCP by default.
Q: What happens if you don't close a JDBC connection?
AmazonAppleTCS
Connection leak! Pool exhaustion — connections never returned to pool. Eventually DB hits max_connections limit and refuses new connections. Always use try-with-resources.
Q: What are ACID properties?
MicrosoftMetaNetflix
Atomicity: all-or-nothing. Consistency: DB moves between valid states. Isolation: concurrent transactions don't interfere. Durability: committed changes survive failures. JDBC handles Atomicity via commit/rollback; Isolation via setTransactionIsolation().
Q: Can ResultSet be used after connection is closed?
GoogleMicrosoft
No! ResultSet is tied to Connection. Closing it invalidates the ResultSet — accessing it throws SQLException. Copy data into List<Map> before closing if needed later.
Q: What is the difference between setFetchSize() and setMaxRows()?
GoogleAmazon
setFetchSize(n): hints to driver how many rows to fetch per network round trip (performance, does NOT limit total rows). setMaxRows(n): hard limit — extra rows silently discarded.
Q: How do you handle a stored procedure with OUT parameters?
GoogleMicrosoft
Use CallableStatement: con.prepareCall("{call proc(?,?)}"). For OUT params: cst.registerOutParameter(index, Types.VARCHAR) before execute(). After cst.execute(), retrieve with cst.getString(index).
Q: What is batch processing in JDBC? How do you implement it?
AmazonMicrosoftInfosys
Sending multiple statements in one network call to reduce round trips. Use pst.addBatch() in a loop, then pst.executeBatch() once. With setAutoCommit(false) and commit every 500-1000 rows — much faster than individual executeUpdate() for bulk inserts.
⑫ Golden Rules — Remember These!
#1ALWAYS use PreparedStatement for user input — NEVER concatenate strings into SQL.
#2ALWAYS use try-with-resources — Connection, Statement, ResultSet all implement AutoCloseable.
#3ResultSet column indices are 1-based. rs.getInt(1) = first column. rs.getInt(0) = exception!
#4executeQuery() → ResultSet | executeUpdate() → int row count | execute() → boolean.
#5JDBC 4.0+ does NOT need Class.forName(). Just add the driver JAR to classpath — SPI handles the rest.
#6Use DataSource + HikariCP in production. NEVER use DriverManager in a web/enterprise app.
#7Transactions: setAutoCommit(false) → execute statements → commit() or rollback() in catch.
#8Batch: addBatch() in a loop, executeBatch() once. Commit every 500-1000 rows for best performance.
#9CallableStatement for stored procedures: {call proc(?,?)} syntax. registerOutParameter() for OUT args.
#10Close resources in reverse order: ResultSet → Statement → Connection.
#11Catch SQLException specifically. Check getSQLState() and getErrorCode() for specific error types.
#12For NULL insertion use pst.setNull(index, Types.X) — never pass Java null directly.
#13setFetchSize() = performance hint (rows per fetch). setMaxRows() = hard limit on row count.
#14Default ResultSet: TYPE_FORWARD_ONLY + CONCUR_READ_ONLY. Specify type if you need scrolling.
#15Can ResultSet be used after connection closed? NO — always copy data into a collection before closing.
